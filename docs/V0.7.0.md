# HealthHub v0.7.0, Food Capture, Product Lookup & Authoritative Recipe Nutrition

HealthHub v0.7 extends the v0.6 Food Library. It does not create a separate store for imported, scanned or externally sourced foods.

## Import pipeline

Spreadsheet paste, CSV and XLSX converge on the same parse, normalise, map, validate, duplicate-preview and import-batch flow. CSV supports UTF-8 and UTF-8 BOM plus common delimiters. XLSX workbooks expose non-empty worksheet names and allow selection before import. Uploads are limited to 5 MB and 10,000 rows.

Canonical columns support `per_serving`, `per_100g` and `per_100ml` nutrition. `serving_quantity` and `serving_unit` describe the user's serving independently from canonical nutrition. Existing v0.6 serving-based foods remain `per_serving` after migration.

## Product identity and lookup

Packaged foods may have multiple identifiers in `food_identifiers`. Barcode lookup is local-first. HealthHub validates common EAN/GTIN lengths and checksum, returns an existing local food when found, and only then invokes the configured external provider.

External lookup uses a provider interface. v0.7 includes Open Food Facts as the first provider. Search and barcode responses are preview candidates, not saved records. Users can correct the candidate before confirming it. Provider failure leaves local foods, manual creation, CSV/XLSX import and label capture available.

## Nutrition label OCR

Nutrition-label capture accepts JPEG, PNG and WebP images up to 10 MB. Tesseract runs inside the HealthHub add-on. HealthHub does not send label images to a third-party OCR service.

The workflow is:

`IMAGE -> OCR -> PARSE -> NORMALISE -> CONFIDENCE/WARNINGS -> USER REVIEW -> VALIDATION -> DUPLICATE CHECK -> SAVE`

Australian label terminology, kJ/kcal, g/mg, per-serving and per-100 g/mL conventions are recognised. Common OCR errors and less-than values are normalised conservatively. Suspicious nutrient relationships generate warnings rather than silently changing values.

A captured label does not become authoritative until the user edits/reviews the extracted values and confirms save. Reviewed records retain packaging-label provenance and verification metadata.

## Provenance and source precedence

Food records can retain source/provider, source identifier or URL, verification status, verified timestamp, OCR confidence and optional image reference. Imports are prevented from silently replacing a higher-quality verified record during duplicate updates. Existing food editing remains possible, while historical diary entries continue to hold immutable nutrition snapshots.

## FoodHub recipe nutrition

FoodHub remains authoritative for recipe identity, serving count and recipe changes. HealthHub remains authoritative for reusable foods, personal serving preferences and nutrition history.

The current FoodHub v1 contract exposes authoritative per-serving recipe nutrition and recipe update timestamps. HealthHub can create or refresh a linked Food Library representation and log it to the diary. The diary entry snapshots the nutrition at consumption time, therefore future FoodHub changes do not rewrite history.

The current FoodHub v1 contract does not expose recipe ingredient quantities. HealthHub v0.7 includes the reusable ingredient-mapping storage foundation but does not claim ingredient-level nutrition calculation is available without that upstream contract. HealthHub does not scrape the FoodHub UI or guess ingredient quantities/conversions.

## Privacy and failure behaviour

Product name/barcode searches are sent to the configured product provider when the user explicitly invokes external lookup. Label images remain local for OCR. No provider credentials are hard-coded. Existing Food Library and manual workflows remain usable if external services are unavailable.

## Migration

Alembic migration `0007_food_capture_products` preserves v0.6 foods, composites, preferences, import history, diary snapshots and planned data. It adds serving/canonical nutrition fields, provenance, barcode identity and FoodHub-link tables without recreating the production database.
