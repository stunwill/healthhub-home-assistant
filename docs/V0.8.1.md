# HealthHub v0.8.1, Daily Diary Image & Barcode Capture

## Why this corrective release exists

v0.8.0 promoted Daily Diary and Quick Add into the primary everyday workflow, but the v0.7 nutrition-label and barcode capture tools were still mainly exposed through the separate Import/Capture screen. v0.8.1 brings those capture paths into the selected diary context.

## Quick Add entry points

Daily Diary Add Food exposes four first-class paths:

- Search
- Scan Barcode
- Take Photo
- Upload Photo(s)

The selected profile, date, meal section, planned/eaten mode and serving quantity remain attached to the workflow.

## Multi-image capture architecture

A capture can contain up to eight JPEG, PNG or WebP images. Each image is validated independently, stored temporarily, processed with local Tesseract OCR, and parsed using the existing nutrition-panel parser introduced in v0.7.

The capture-session merge layer combines parsed values into one review candidate. Higher-confidence values win. If two images produce different values at the same confidence level, HealthHub records a conflict warning rather than silently choosing one.

The response records which upload supplied each merged field so the architecture can support richer source-attribution UI later.

Processing is intentionally sequential rather than unbounded parallel OCR. Tesseract is CPU-heavy and HealthHub normally runs on Home Assistant-class hardware, so bounded host resource usage is preferred over maximising throughput for the small number of images in a household food capture.

## Human verification and direct diary use

OCR never creates a food automatically. The user must review and may correct the extracted product name, brand, barcode, serving details and nutrition fields.

`Save & Add to <meal>` then:

1. reuses an existing local food when a reviewed barcode already matches;
2. otherwise saves the reviewed packaging-label food to HealthHub's Food Library;
3. creates either a consumed diary entry or Planned entry according to the preserved context;
4. reloads the selected Daily Diary;
5. removes temporary capture images.

The diary/planned entry continues to use HealthHub's immutable nutrition snapshot behaviour.

## Barcode capture

The diary barcode flow supports the browser BarcodeDetector API where available, plus manual EAN/UPC entry. HealthHub checks local food identity first and only uses the configured external product provider when needed.

Local matches can be added directly to the selected meal. External matches require the existing human product review/save path before being added. If camera scanning is unavailable or a barcode cannot be resolved, the user can continue with photo capture without losing the selected diary context.

Static uploaded-image barcode decoding is not introduced by v0.8.1 because the existing v0.7 implementation provides live BarcodeDetector scanning rather than a server-side image barcode decoder. A barcode visible in a package photo can still be entered during verification.

## Local-first and privacy behaviour

Nutrition OCR remains fully local to the HealthHub add-on. FoodHub is not required for image capture, OCR review or diary insertion. External product lookup is optional enhancement for barcode identity and does not block local OCR.

Source images are temporary. They are deleted after successful verified save, and partial files are removed if a multi-image request fails validation.

## Mobile behaviour

Take Photo uses the browser's environment-facing capture hint. Upload Photo(s) supports multiple existing images. The Quick Add sheet uses stacked controls at narrow widths, responsive image thumbnails and no horizontal overflow.

Camera permission failure does not terminate the Add Food workflow. Manual barcode entry and photo upload remain available.

## Performance instrumentation

The capture pipeline logs high-level timings for:

- upload/validation
- Tesseract OCR
- per-image total processing
- complete capture-to-verification duration

Raw OCR text and image contents are not written into performance logs.

## Migration

No database migration is required for v0.8.1. Capture sessions are transient workflow state layered over the existing v0.7 Food Library/OCR structures and v0.8 Diary/Planning structures.
