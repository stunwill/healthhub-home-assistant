# HealthHub v0.8.0, Daily Diary, Meal Planning & Planner Responsiveness

## Daily diary

v0.8 promotes the diary into the primary everyday workflow. The selected-date view separates consumed food from planned food and organises entries into Breakfast, Morning Snack, Lunch, Afternoon Snack, Dinner, Evening Snack and Drinks.

The calorie budget shows Daily Goal, Eaten, Planned and Remaining after planned food. Planned food is never treated as already consumed. Protein, carbohydrates, fat and sugar are shown as supporting daily totals.

## Snapshot behaviour

Consumed diary entries and planned entries continue to store nutrition snapshots. Editing serving quantity scales the stored snapshot proportionally. Copying consumed or planned items to another date creates a new Planned snapshot, so later Food Library or FoodHub changes cannot silently rewrite the copied plan.

Marking a planned item eaten creates a consumed diary entry from the existing planned snapshot.

## Reusable meals

Migration `0008_saved_meals` adds profile-scoped reusable meal definitions. Saved meal items reference Food Library records and store the user's serving quantities. Adding a saved meal to a plan creates normal independent planned snapshots.

## Search and FoodHub

v0.8 splits interactive search into local HealthHub search and optional FoodHub search. The frontend displays local results first, then merges FoodHub recipe results if they arrive. Stale requests are cancelled with AbortController.

Local ranking favours profile favourites, use count and recency. A FoodHub recipe that has already been linked into the local Food Library is not shown again as a separate external result.

FoodHub requests use a persistent pooled HTTP client with keep-alive. The client is closed during application shutdown. FoodHub failure does not block local Quick Add.

## Planner performance

The previous weekly summary implementation performed two data queries for every day of a seven-day week, 14 data queries in total. v0.8 performs one planned-entry range query and one consumed-entry range query, then groups those records by local date in application memory.

The previous recurrence materialiser performed a database existence lookup for each candidate occurrence. v0.8 fetches the existing occurrence timestamps once for the horizon and uses an in-memory set while creating missing entries.

The Week Add to Plan action now immediately enters an `Adding…` state, prevents duplicate in-flight submissions, and uses the returned planned entry to reconcile a one-off addition without waiting for a blocking full-week reload.

## Performance targets

The release is designed for the following normal household-data targets on the Home Assistant host:

- visible Add to Plan feedback within 100 ms
- local planned-entry API responses ideally within 250 ms
- visible one-off additions around 300 ms
- weekly-plan responses within 250 ms
- local predictive search within 200 ms
- ordinary recurrence creation comfortably below one second

Wall-clock thresholds are not enforced on shared CI runners. Regression coverage focuses on query architecture and functional behaviour instead.

## Compatibility

Existing v0.7 data is preserved. Legacy `snack` meal-period values remain valid and are displayed in the afternoon snack section by the frontend. No authentication layer is introduced; Home Assistant remains the trust boundary.
